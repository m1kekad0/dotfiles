# AGENTS.md（グローバル共通ルール）

> 本ファイルは、複数のコーディングエージェント（Claude Code / ChatGPT Codex / Google Antigravity / xAI Grok 等）で共用するグローバル設定であり、すべてのプロジェクトで共通して適用することを目的とする。
> エージェント固有のルールを追加する場合は、対象を見出しで明示する。

IMPORTANT: 以下のルールは、すべての会話およびタスクに適用する。各実行環境（プラットフォーム／エージェント側）の上位指示に従ったうえで、より具体的な指示を次の優先順位で適用する。

1. ユーザーからの個別指示（会話中の指示）
2. プロジェクト配下の AGENTS.md およびコーディング規約
3. 本ファイル

## 言語

- ユーザーへの応答、およびユーザーへ提示する作業状況・説明・判断根拠・要約は、すべて日本語で記述する。英語で応答してはいけない。
- コミットメッセージ、PR タイトルおよび PR 本文もすべて日本語で記述する。
- コードの doc コメントおよびインラインコメントは、原則として日本語で記述する。ただし、プロジェクト固有の言語規約がある場合は、その規約を優先する。
- ファイル名、識別子、コマンド、プログラミング言語の構文、製品名、ライブラリ名、ログおよびエラーメッセージの原文などは、必要に応じて原語のまま記述してよい。

## ソースコード実装

- doc コメント（Javadoc、JSDoc、docstring 等）は以下の基準で記載する。
  - public / protected および外部利用者に公開される要素（HTTP API、export された要素、ライブラリの公開インターフェース、公開 DTO 等）: 必須
  - private な要素や内部実装: 一律には要求しない。コードだけでは目的、前提、制約または判断理由が分かりにくい場合に記載する。
- インラインコメントでは、処理内容の単なる言い換えではなく、実装の意図、前提、制約または判断理由を補足する。
- 既存プロジェクトにコーディング規約やコメント規約がある場合は、その規約を優先する。

## GitHub Pull Request 操作

- PR を編集、更新または操作する前に、対象 PR が open 状態であることを確認する。確認方法は、利用可能なツールと状況に応じて選択する（例: `gh pr view`、`gh pr list --state all`）。
- merged または closed 状態の PR は編集しない。
- 対象 PR が open でない場合でも、ユーザーから明示的な依頼がない限り、新しい PR を作成しない。
- PR の作成、コメント投稿、レビュー送信、マージなど、外部状態を変更する操作は、ユーザーの依頼範囲内でのみ実行する。

## 言語・フレームワーク固有ルール

対象の技術スタックを扱うタスクでは、以下の該当セクションを適用する。プロジェクト固有の規約・設定がある場合は、そちらを優先する。
（注: 本セクションが肥大化した場合は、言語ごとに個別ファイル（例: `~/AGENTS/java-springboot.md`）へ切り出し、本体から「対象技術を扱う場合は該当ファイルを必ず読み、適用する」と参照する方式へ移行する。）

### Java / Spring Boot

- 対象プロジェクトで指定された Java、Spring Boot、ビルドツールのバージョンと既存の設計・命名・フォーマット規約を優先する。
- 依存性注入は原則としてコンストラクタインジェクションを使用し、フィールドインジェクションは避ける。
- Controller は HTTP 入出力と検証・変換に責務を絞り、業務ロジックは Service 等の適切な層へ配置する。
- 入力値は Bean Validation 等で宣言的に検証し、例外と HTTP レスポンスの変換は既存方針に従って一元化する。
- トランザクション境界は業務ユースケース単位で明示し、原則として Service 層に置く。外部 API 呼び出しを含む長時間トランザクションは避ける。
- Entity を API の入出力へ直接公開せず、必要に応じて DTO へ分離する。ただし既存アーキテクチャが異なる場合はそれを優先する。
- 設定値と秘密情報をソースコードへ直書きせず、Spring の設定機構と実行環境の秘密管理を利用する。
- 変更には影響範囲に応じた単体テストまたは統合テストを追加・更新し、可能な限りプロジェクト標準のビルド／テストで検証する。
- DB スキーマ変更は既存のマイグレーション方式に従い、既存データとロールバック／後方互換性への影響を考慮する。

### Next.js（TypeScript / React）

- 対象プロジェクトの Next.js バージョン、ルーティング方式（App Router / Pages Router）および既存の規約・設定（ESLint、Prettier、tsconfig 等）を優先し、独断でルーティング方式の移行を行わない。
- App Router のプロジェクトでは Server Components を既定とし、`"use client"` は state・イベントハンドラ・ブラウザ API が必要なコンポーネントに限定する。
- データの読み取りは原則として Server Components で行い、Route Handlers は HTTP 境界が必要な場合に、Server Actions は主に更新処理に使用する。クライアント側 fetch は必要な場合に限定する。
- プロジェクトの tsconfig に従い、可能な限り安全な型付けを行う。`any` より `unknown` や具体型を優先し、`any` がやむを得ない場合は理由をコメントで明記する。
- 過度な抽象化や早すぎる共通化を避け、まず具体的に実装し、重複が明確になった時点で共通化する。
- クライアントへ公開する必要がある環境変数のみ `NEXT_PUBLIC_` プレフィックスを付け、秘密情報には決して付けない。
- 変更後はプロジェクト標準の lint・型チェック・テストを実行して検証する。
